# Hetzner CCX33 run, 2026-10-09

- **Machine**: Hetzner Cloud CCX33 in Ashburn: 8 dedicated vCPUs (AMD EPYC-Milan, KVM guest), 31 GB, Linux 6.8, Node 22.23. Leased for this run and deleted afterwards. Every suite ran pinned to CPUs 1 to 7. The VM exposes no CPU frequency governor, so none was set (`machine.json`, `lscpu.txt`).
- **What ran**: `scripts/run-dedicated.sh` with `PASSES=5 COLD=20`, from 23:39 to 00:11 UTC: the CPU-limit check, five passes of the size matrix, memory, ten plugins, then Node hosting.
- **Uneven sample counts**: each matrix pass ran in one workerd process, and every one of the five crashed (segmentation fault or abort) after finishing 26 to 37 of the 55 payloads, about 1,100 to 1,600 plugin isolates in. The same crash reproduces on a smaller machine as a V8 "JavaScript heap out of memory" in the harness. A payload got a pass's 20 loads only when it came early enough in that pass's shuffled order, so each payload has 20 to 100 cold loads (`samples` in `summary.json`), and nothing measured during a pass looks affected: the paired tiny-plugin loads held at 22 to 28 ms from start to crash in every pass, and the 95% ranges are within a few percent. Since then `run-all.mjs` starts a fresh workerd for every four payloads (`CHUNK`) and retries a chunk that dies; a one-pass test run finished all 55 payloads without a crash.
- **Machine speed**: with the same method, every payload took 2.8 to 5.1 times as long here as on a shared 4-vCPU Intel Xeon VM (`results/shared-xeon-4vcpu/`), 4.1 times at the median. That includes an almost empty plugin (26.8 ms here, 7.1 ms there) and plain data, so the whole sandbox start-up is slower here, not only compiling. Absolute times here are not production times, and neither are the Xeon VM's. One possible cause, not tested: this guest's kernel runs software workarounds for CPU security flaws (Retpolines, and SRSO "Safe RET" without microcode support, in `lscpu.txt`), which make page faults and memory mapping slower, and starting an isolate does a lot of both.
- **Node hosting**: a first attempt failed with "Address already in use" because the old port range overlapped Linux's ephemeral ports; bf6e340 fixed it, and `node-host.jsonl` comes from the rerun.
- **Report**: `report.html` here is built with
  `RESULTS_DIR=results/hetzner-ccx33-ash COMPARE_DIR=results/shared-xeon-4vcpu COMPARE_LABEL="a shared 4-vCPU Intel Xeon cloud VM measured the same way" COMPARE_SHORT="Shared Xeon VM" EDGE_DIR=results/cloudflare-edge node report/build-report.mjs`
  and is also the checked-in `report/plugin-size-benchmark.html`, with the Cloudflare run from `results/cloudflare-edge/`.
