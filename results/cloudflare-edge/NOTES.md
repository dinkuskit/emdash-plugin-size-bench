# Cloudflare run, 2026-10-10

- **Where**: Cloudflare's ATL location (every row), on a Workers Paid account with Worker Loader. The test Worker in `edge/` (compatibility date 2026-08-20, wrangler 4.149.0) was deployed for each run and deleted straight after. It loads each plugin the way EmDash 1.2.0's `CloudflareSandboxRunner` does: EmDash's generated wrapper plus the plugin as a second module, compatibility date 2026-04-01, `globalOutbound: null`, `cpuMs` as given and `subRequests: 10`.
- **What ran**: `MODE=all PASSES=3` from about 01:36 UTC (241 s). Every payload, three passes in shuffled order, five fresh loads each at `cpuMs` 50 and 30000, then the CPU-limit search for the almost empty plugin, every real plugin, and eager and lazy code up to 2 MB. Then `MODE=control` at about 01:56 UTC (`edge-control.log`): busy-loop plugins that run the local limits suite's loop 2 to 1,000 million times in their route or at import, three fresh loads at each limit plus two later calls into the first one, and the search for four of them.
- **Times**: wall time measured inside the test Worker with `Date.now()` around the Worker Loader call, so 1 ms resolution. A first call includes getting the stub, creating the isolate, compiling and running the plugin's modules, and the route call.
- **Bridge**: `diag.json` shows that the deployed Worker's `exports` and `ctx.exports` held only `default`, with no `BenchBridge`, although the Worker exports that entrypoint and both are present under `wrangler dev`. So every plugin got a placeholder bridge. None of the routes used here touch the bridge. Two earlier deploys that evening stopped at this point before measuring anything (they built the bridge inside Worker Loader's callback) and left no rows. EmDash's runner takes its `PluginBridge` from the same `exports`, so a deployed EmDash site may be worth checking for the same thing.
- **Results**: no first call failed at 50 ms (0 of 840, plugins up to 8 MB), and every plugin up to 2 MB still loaded and answered with the limit set to 1 ms, the lowest the search tries. Busy loops at import never failed, even one that kept the first call busy for about 8 s at 50 ms. Busy loops in a route passed at 50 ms on first calls of up to about 1.5 s. The only failure was `Worker exceeded CPU time limit.` on the third call into the 300-million-step route loop, whose earlier calls had each run about 1.5 s. That matches Cloudflare's documentation: each isolate "has some built-in flexibility" for infrequent overruns, and a Worker that keeps hitting the limit is stopped. So the one-off cost of loading a plugin did not trip EmDash's limit. These runs cannot tell whether that cost is charged against the same flexibility, because no plugin here both loaded slowly and then kept running over.
- **Limits of this run**: one location, one account, one evening. The ATL numbers include Worker Loader's own overhead, about 14 ms for an almost empty plugin.
