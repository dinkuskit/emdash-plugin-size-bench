EmDash 1.2.0 · sandboxed plugins

Plugin Size Benchmark

How much does a bigger sandboxed (Registry) plugin cost to load? We loaded 57 plugins, from 5 KB to 8 MB, through EmDash's own CloudflareSandboxRunner and Worker Loader, 21 times each in fresh isolates, and measured the first call, later calls, memory, sites with ten plugins, and Node hosting.

Prepared by DinkusKit for the EmDash maintainers · local workerd 1.20261006.1 on a 4-vCPU Xeon VM

What we found

  • Size only costs on the first call into a new isolate. Every later call took 0 to 1 ms at every size up to 8 MB.
  • What the code does at load matters more than its bytes. Code that runs at import costs about ms per extra MB on this machine. The same code wrapped so it runs later costs about ms per MB, and plain data about ms per MB. DinkusKit Commerce (114 KB) loads faster than Inventory's 74 KB build.
  • Up to 256 KB, the first call stays under about 70 ms even for worst-case code that runs everything at import. 1 MB costs about ms and 8 MB about ms.
  • Memory grows about 9 MB per MB of run-at-import code, on top of about 1.2 MB for an empty isolate. That puts a single plugin near the 128 MB isolate ceiling at roughly 12 to 14 MB of code.
  • Several plugins add up. On a cold site, ten 1 MB plugins woken one after another (for example, ten save hooks on one content save) took about ms. Ten copies of today's Commerce took ms.
  • Local workerd ignores the 50 ms CPU limit, so whether a big plugin's first call would fail in production is still open. The callout below explains why.

The open question: does start-up count against the 50 ms CPU limit?

EmDash gives each sandboxed call cpuMs: 50 through Worker Loader (packages/cloudflare/src/sandbox/runner.ts, DEFAULT_LIMITS). Local workerd does not enforce it: a plugin that spins for 3 seconds at import, or inside a route, still succeeds under the production limits (table below).

On the edge, if parsing and running a module's top level count toward the first call's 50 ms, then run-at-import code past roughly 192 KB on this machine's speed would fail on its first call. Lazy code would reach that point near 1 MB. The edge folder in the benchmark measures exactly this on real Cloudflare.

How it was measured

  1. Each plugin goes through CloudflareSandboxRunner.load() from @emdash-cms/cloudflare@1.2.0, then one invokeRoute(). That is the same Worker Loader binding, generated wrapper and PluginBridge a Cloudflare-hosted site uses. The harness runs inside workerd through @cloudflare/vitest-plugin.
  2. Every cold load gets a new isolate key and a unique source comment, so nothing is reused. Loading the same source twice gave the same times, so we saw no compile cache.
  3. Synthetic plugins are built from real minified libraries (dayjs, marked, moment, lodash, luxon, rxjs, handlebars, date-fns, acorn, three, typescript) in three shapes. Run at import initialises every library on load, which is what a bundled ESM plugin does. Run later wraps the same code in functions called only on demand. Plain data puts the same bytes in one string.
  4. The timer is Date.now() inside workerd around the awaited call. A Node-side clock agreed with it.

Not covered

  • Real edge hardware and the enforced CPU limit. A deployable worker for that is included.
  • Downloading a bigger bundle from the Registry at install, and reading backend.js from R2 on every cold start of the host (loadBundleFromR2).
  • Absolute numbers on production machines. Read this page for shape and ratios.
